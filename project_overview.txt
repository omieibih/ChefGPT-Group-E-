  SECTION 1: WHAT EVERY FILE DOES
================================================================================

--- ROOT FILES ---

app.py
    This is the main file that starts the whole app. It loads the secret keys
    from the .env file, sets up the Firebase connection, and registers all the
    different pages and features. It also has a few simple helper functions
    (like save_recipe and get_nutrition) that the test files use so tests don't
    need a real internet connection to run.

requirements.txt
    A list of all the Python libraries the project needs. Running
    "pip install -r requirements.txt" installs everything at once.

.env
    A file that stores secret keys like the Groq API key and Firebase credentials.
    It is NOT uploaded to GitHub because it contains sensitive information.

.gitignore
    Tells Git which files to ignore and not upload. Mainly used to keep .env
    and the virtual environment folder off of GitHub.

README.md
    A description of the project, how to set it up, and how to run it.


--- backend/Core/ ---

backend/Core/firebase_init.py
    Connects to Firebase when the app first starts. If it can't connect
    (for example, if the credentials are wrong), it sets a flag saying Firebase
    is unavailable instead of crashing the whole app.

backend/Core/auth_helper.py
    A small helper that checks if a user is logged in on any API request.
    It reads the login token the browser sends, asks Firebase to verify it,
    and returns the user's info if valid. If the token is missing or invalid,
    it returns nothing so the route can send back a "not logged in" error.

backend/Core/__init__.py
    An empty file that just tells Python this folder is a package.


--- backend/Components/ ---

backend/Components/__init__.py
    Collects all the feature blueprints into one list so app.py can register
    them all in one place.

backend/Components/pages.py
    Handles the basic page navigation. When you go to the home page it shows
    the experience level form. When you submit that form it loads the ingredients
    page. When you go to /login it shows the login page. No business logic here,
    just routing.

backend/Components/recipes.py
    The most important file in the project. When the user submits their
    ingredients, this file builds a prompt and sends it to the LLaMA AI model
    through the Groq API. The AI sends back a list of 3 recipes as JSON, which
    this file parses and sends to the results page to display. If anything goes
    wrong with the AI call, it catches the error and shows a message to the user
    instead of crashing.

backend/Components/favorites.py
    Lets users save recipes they like. When a user clicks "Save Recipe" on the
    results page, this file stores the recipe in Firebase under their account.
    Users can also view all their saved recipes and delete ones they don't want
    anymore. Before deleting, it checks that the recipe actually belongs to the
    user requesting the delete.

backend/Components/shopping_list.py
    Lets users keep a shopping list. Users can add ingredients, check them off,
    and remove them. Everything is saved in Firebase under the user's account so
    it persists between sessions.

backend/Components/nutrition.py
    Fetches nutrition info (calories, protein, fat, carbs) for a meal by calling
    the Edamam Nutrition API. This gets called automatically on the results page
    to add a nutrition section to each recipe card.

backend/Components/experience_level.py
    Saves and retrieves the user's preferred cooking experience level from
    Firebase. This way the app can remember the user's level between sessions
    if needed.

backend/Components/ingredient_suggestions.py
    Powers the floating assistant bubble on the ingredients page. It looks at
    the user's saved favorite recipes and suggests ingredients they might want
    to add based on what they've liked before. If the user has no favorites yet,
    it falls back to a small list of common ingredients. It also has an "I'm
    Feeling Lucky" mode that gives random suggestions.

backend/Components/dietary_filters.py
    A utility function that filters a list of recipes down to only the ones
    that match a dietary restriction (like vegan or gluten-free). It checks each
    recipe's dietary_tags list and returns only the ones that match. Mainly used
    in the unit tests.


--- static/ ---

static/firebase-config.js
    Sets up the Firebase connection on the browser side. It exports an "auth"
    object and a "db" object that all the other JavaScript files import and use.

static/auth.js
    Handles everything on the login page. It connects the Log In, Create Account,
    and Sign In with Google buttons to Firebase. If login fails it shows the
    error message from Firebase. If the user is already logged in it redirects
    them to the home page.

static/assistant.js
    Controls the floating assistant panel on the ingredients page. It handles
    opening and closing the panel, fetching personalized ingredient suggestions
    from the backend (sending the user's login token so the server knows who
    to suggest for), turning suggestions into clickable buttons, and adding
    clicked ingredients into the input field without duplicates.

static/style.css
    The stylesheet for the whole app. Controls colors, fonts, button styles,
    the recipe cards, the nav bar, the floating assistant button, and how things
    look on smaller screens.


--- templates/ ---

templates/login.html
    The login page. Has email and password inputs plus buttons for logging in,
    creating an account, and signing in with Google. Loads auth.js to handle
    all the actual login logic.

templates/index.html
    The home page. Shows a dropdown to pick your cooking experience level
    (Beginner, Intermediate, or Advanced) and a Next button. Redirects to
    the login page if the user isn't signed in.

templates/ingredients.html
    The ingredient input page. Shows the experience level the user picked,
    and has fields for entering ingredients, an optional budget, and an optional
    dietary filter. Also has the floating assistant bubble HTML that assistant.js
    controls.

templates/results.html
    The results page. Uses a Jinja2 loop to display each of the 3 recipes the
    AI generated as expandable cards. Each card shows the recipe name, description,
    ingredients you have, ingredients to buy, and step-by-step instructions.
    There's a "Save Recipe" button on each card. After the page loads, a script
    also fetches and appends nutrition info to each card.

templates/favorites.html
    The My Favorites page. When it loads, JavaScript fetches all the user's saved
    recipes from the backend and displays them as expandable cards. Each card has
    a Remove button. Shows a loading message while fetching and an empty state
    message if no favorites have been saved yet.

templates/shopping_list.html
    The Shopping List page. Loads the user's saved items from the backend and
    shows them as a list with checkboxes and remove buttons. Has a form at the
    top to add new items.


--- tests/ ---

tests/test_app.py
    The main test file. Tests that pages load correctly, that the /results route
    only accepts POST requests, and that get_recipes() returns the right structure.
    It mocks the Groq API so tests run without a real API key. Also tests that
    the results page shows an error message when the AI call fails.

tests/test_dietary_filters.py
    Tests the dietary filter function. Makes sure it returns only recipes that
    match the filter, returns empty for unrecognized filters, and handles empty
    or None input without crashing.

tests/test_experience_level.py
    Tests that the experience level is correctly passed from the home page through
    to the recipe generation call. Also tests that the backend defaults to
    "Beginner" if no experience level is submitted.

tests/test_IngredientSuggestion.py
    Tests the ingredient suggestion system. Tests the basic keyword-matching mock
    (high protein, cheap, vegan, etc.) and also tests the real suggestion
    algorithm to make sure it parses ingredients correctly, adds title-based hints,
    and falls back to defaults when there are no favorites.

tests/test_nutrition.py
    Tests the nutrition mock function in app.py. Makes sure it returns the right
    keys, that values are non-negative, that empty input returns an error message,
    and that lookups work regardless of letter case.

tests/test_SaveRecipeToFavorites.py
    Tests saving and removing favorites using the in-memory mock functions in
    app.py. Tests saving a recipe, checking it shows up in the list, saving
    multiple recipes, preventing duplicates, and removing a recipe.


--- .github/ ---

.github/workflows/main.yml
    The automated CI/CD pipeline on GitHub. Every time code is pushed to main,
    it automatically installs dependencies, runs all the tests, and if they pass,
    deploys a static preview to GitHub Pages.


--- .vscode/ ---

.vscode/tasks.json
    A VS Code shortcut that lets you run just the ingredient suggestion tests
    from the VS Code Tasks menu without typing the command manually.


================================================================================
  SECTION 2: COMPLEXITY, SECURITY, RELIABILITY, AND ARCHITECTURE
================================================================================

--- ARCHITECTURE ---

The project is organized into three main layers:

  1. The entry point (app.py) starts everything up.

  2. The backend has two parts:
       - backend/Core/ handles shared stuff that every feature needs:
         connecting to Firebase and checking if users are logged in.
       - backend/Components/ has one file per feature (recipes, favorites,
         shopping list, etc.). Each file handles its own routes and database work.

  3. The frontend (static JS files and HTML templates) talks to the backend
     through API calls. The browser handles login with Firebase, and the server
     double-checks that login before doing anything with user data.

The app uses three outside services:
  - Groq API (LLaMA AI) to generate recipes
  - Firebase for user login and storing data (Firestore database)
  - Edamam API for nutrition information


--- STRUCTURAL COMPLEXITY ---

Structural complexity is about how many connections there are between the
different parts of the code and how complicated those connections are.

We kept structural complexity low. Each feature file only talks to the Core
files (Firebase and auth), not to other feature files. The dependency chain
is simple:

  app.py -> feature blueprints -> Core (auth + Firebase)

There are no circular dependencies. Adding a new feature just means writing
one new file and adding one import to Components/__init__.py. The rest of
the app doesn't change.


--- DATA COMPLEXITY ---

Data complexity is about how the data in the program is structured and how
different pieces of data relate to each other.

The data structures in this project are simple. There are only three types
of data stored in the database:

  - Favorites: a recipe name, ingredients list, and instructions stored
    under the user's ID.
  - Shopping list items: a name and a completed (true/false) flag, stored
    under the user's ID.
  - User profile: just their ID, email, and experience level.

Recipe data from the AI is temporary -- it's shown on the results page but
never saved to the database unless the user clicks "Save Recipe."

The most important data flow is the login token: the browser gets a token
from Firebase, sends it with every API request, and the server uses it to
figure out who's asking and what data they're allowed to see.


--- DECISION COMPLEXITY ---

Decision complexity is about how many branching decisions (if/else logic) the
program has to make and how complicated those decisions are.

Most decisions in this project are simple yes/no choices:

  - Is the user logged in? If not, return an error.
  - Did Firebase connect successfully? If not, return an error.
  - Was a budget provided? If so, include it in the AI prompt.
  - Was a dietary filter provided? If so, include it in the AI prompt.
  - Does the ingredient the user clicked already exist in the input? If so,
    don't add it again.

Each decision is handled in one small place and doesn't rely on anything
complicated. The most complex logic is in the AI prompt itself, but that
complexity belongs to the AI model -- our code just sends the inputs and
handles whether the response worked or failed.


--- SECURITY ---

Three main security measures were used:

  1. Server-side login verification.
     When the browser sends a login token with a request, the server doesn't
     just trust it. It calls firebase_auth.verify_id_token() which checks the
     token's signature against Google's servers. A user can't fake this.

  2. Ownership check before deleting.
     Before deleting a saved favorite, the code reads the record from the
     database and checks that its owner ID matches the person making the
     request. This stops one user from deleting another user's data even if
     they somehow knew the record's ID.

  3. Preventing XSS attacks.
     Any time user-typed text gets placed into the page's HTML by JavaScript,
     it goes through an escapeHtml() function first. This replaces characters
     like < and > so malicious HTML or scripts can't be injected into the page.

Secret keys (the Groq API key, Firebase credentials) are stored in the .env
file on the server and never sent to the browser.


--- RELIABILITY ---

Several things were done to make sure the app doesn't break or confuse users
when something goes wrong:

  1. The AI call is wrapped in a try/except. If the Groq API fails or returns
     something unexpected, the results page shows an error message instead of
     crashing.

  2. If Firebase fails to initialize at startup, a flag is set so every API
     route can return a friendly error message instead of throwing a crash.

  3. The assistant panel shows a loading message and clears old suggestions
     before fetching new ones so users never see stale or misleading data.

  4. The favorites and shopping list pages force-refresh the login token before
     making requests, which prevents errors from expired tokens.

  5. All fetch() calls in the frontend are wrapped in try/catch so a network
     failure shows a readable error message instead of silently doing nothing.
